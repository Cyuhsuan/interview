# 牙科預約 Bot — 架構筆記（內部用）

先講假設：這系統是要真的上線給病患用的，不是本機 demo。規模就照 README 那樣，一間診所、三個人、五種服務。

## 架構長怎樣

- 後端：Go 寫的，全部塞在一個 process 裡面，內部再分模組（Catalog / Scheduling / Booking / Conversation / Calendar），每個模組裡面又分 handler → service → repository 三層。
- 資料庫：PostgreSQL，預約這件事一切以它為準。
- 前端：React + TypeScript，主要用打字聊天，語音是加分項。
- 外部行事曆（Google/Microsoft）：只能被動接收我們寫進去的資料，不能拿它來判斷有沒有空檔，用 outbox 這套機制非同步寫進去。
- AI：只負責聽懂病患在講什麼、抓出候選值，「這時段到底能不能訂」永遠是後端的確定性程式碼說了算，AI 沒有決定權。

現況：Catalog/Scheduling/Booking/Conversation/語音輸入這些都做完了，Calendar 的 outbox 機制也做完了，但現在接的是一個假的 sandbox adapter，還沒接真正的 Google/Microsoft OAuth（在等診所那邊決定要用哪種授權方式）。取消/改期第一版沒做，直接請病患打電話給診所。

## 為什麼這樣選

**PostgreSQL 說了算，Google/Microsoft 只能單向寫入**：外部行事曆查詢有延遲、有配額限制，如果拿它來判斷空檔，兩個病患同時看到「這格是空的」馬上就會出事。所以判斷邏輯全部收在資料庫裡，用資料庫的排他約束直接擋掉重複預約，比自己寫一套分散式鎖靠譜多了。就算外部行事曆掛掉，病患照樣訂得到位，只是診所那邊的行事曆暫時看不到而已。

**用 outbox，不是同步呼叫 Calendar API**：如果訂位當下就同步去打 Google API，病患等的時間就會被 Google 的延遲拖累，而且萬一打失敗了，要不要把已經訂好的預約撤掉也很麻煩（撤掉的話病患會覺得「明明訂到了怎麼又被取消」，更難看）。所以把「訂位成功」跟「同步到行事曆」這兩件事拆開：PostgreSQL 寫進去就算成功，馬上回應病患，外部同步狀態如實回報進度，失敗就一直重試，重試到底也不會動到已經確認的預約。

**先做一個假的 sandbox adapter，不急著接真的 OAuth**：Google/Microsoft 要用哪種授權方式，是診所那邊要拍板的組織層級決定（例如要不要開 Workspace 的 delegation 權限），工程這邊沒辦法自己決定。與其卡在這件事上不動，不如先把整套 outbox 狀態機、重試邏輯、worker 都做完測完，等診所那邊決定好授權方式，只要換掉一個 adapter 就好，其他程式碼完全不用動。

**AI 只負責聽懂話，不負責判斷合不合法**：AI 講話會有機率性、會出錯，牙科預約牽涉到真的時段有沒有衝突，不能讓 AI 直接拍板。就算 AI 抓錯候選值，最壞情況也只是機器人回一句答非所問，絕對不會真的訂出一個衝突或不存在的時段。

**第一版不做取消/改期**：現在沒有帳號系統，根本沒辦法確認「來取消的人是不是本人」，硬做的話風險比省下來的麻煩還大，所以先都轉給人工處理。

## 正式上線要花的成本

**還沒做完的事**：
- 真的接上 Google/Microsoft OAuth——工程量不算大，卡點是診所要先決定授權方式、拿到權限
- JWT session 驗證、CSRF、rate limiting——文件上都寫了規則，**但程式碼目前完全沒寫**，這是上線前最大的一個坑
- Calendar 憑證要怎麼加密存、金鑰怎麼管理，都還沒做
- idempotency key 過期之後要清掉的排程，現在也沒有
- 語音功能在不同瀏覽器上到底能不能用、前端的自動化測試，都還沒補齊

**要花的錢**：
- PostgreSQL 得用有備份、能還原到任意時間點的雲端服務，不能自己隨便架一台
- AI 對話擷取跟語音轉錄都是按用量算錢的，正式要用哪家供應商還沒定案，現在算不出實際費用
- Google/Microsoft 的 API 有叫用配額限制，worker 重試的頻率要小心調，不然會被限流
- 密鑰、連線字串這些現在放在 `.env` 裡，正式上線要換成有管理的 secret 服務

## 安全功能：已經做的

- ID 全部用真隨機亂數產生，猜不到
- 用版本號（ETag/If-Match）擋同時改同一筆資料互相覆蓋
- 資料庫本身就會擋同一個人同時段被重複約進去，不是只靠程式碼邏輯把關
- 同一個請求重複送不會建立出兩筆預約
- 查不到有沒有空檔時直接回錯誤拒絕服務，不會亂猜一個結果給病患
- 記錄只存誰、做了什麼、什麼時候，不存病患姓名、email、聊天內容
- 行事曆同步失敗的訊息會先過濾過，不會把外部服務回傳的原始內容存下來
- 錯誤訊息統一格式，不會不小心把程式內部細節、SQL、病患資料洩漏出去
- 環境變數少設一個系統就直接開不起來，不會偷偷套用一個危險的預設值頂著
- 語音上傳有檔案類型限制，也限制檔案大小上限
- 病患問到看診、開藥、報價、保險、取消改期這些，機器人一律拒答並轉人工，而且不會偷偷把當下對話內容套用到訂位資料裡
